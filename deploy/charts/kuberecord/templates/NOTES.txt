exist. Three steps from here.

1. Credentials. The operator reads sink credentials from Secrets in its own
   namespace only — that is the whole of its Secret grant, and it is what makes
   a cluster-scoped sink unable to reach a Secret somebody else owns.
{{- if $secrets }}

   The sinks below name these Secrets. Create each one, if you have not already:
{{- range $secrets }}

     kubectl create secret generic {{ .name }} \
       --namespace {{ $.Release.Namespace }} \
       {{ join " \\\n       " .literals }}
{{- end }}
{{- else }}

     kubectl create secret generic <name> \
       --namespace {{ .Release.Namespace }} --from-literal=password='<your-password>'

   An S3Sink on a cloud provider needs no Secret at all: omit spec.credentials
   and it authenticates from the ambient chain (IRSA, workload identity or an
   instance role), so no long-lived key exists to leak.
{{- end }}

2. Your sinks. This release created {{ len .Values.sinks }}:
{{- range .Values.sinks }}

     kubectl get {{ .kind | lower }} {{ .name }} -o jsonpath='{.status.conditions}'
{{- end }}
{{- if $chSinks }}

   On a ClickHouseSink, Ready=True means it dialled ClickHouse and validated the
   schema v1 tables. SchemaValid=False names the columns that do not match; apply
   deploy/clickhouse/schema/*.sql, or add --ch-auto-create-schema to `extraArgs`
   to let the operator apply the shipped DDL itself.
{{- end }}
{{- if $s3Sinks }}

   On an S3Sink, HistoryUnavailable=True is expected and permanent, on a healthy
   sink: it is a Writer-only archive tier (D12) that cannot read back what it
   wrote, so cache warm-up, zombie GC and boot reconciliation are disabled for it
   and every record is a full Snapshot. Ready=True is still the health signal.
   BucketReachable=False names a bucket that does not exist, cannot be
   authenticated to, or lacks the Object Lock this sink asks for.
{{- end }}
{{- else }}

2. A sink. Create a ClickHouseSink or an S3Sink and name it whatever the rules
   below will name in spec.sink, or let this chart create it — the `sinks` value
   takes a list of {kind, name, spec}, with spec passed through verbatim:

     helm upgrade {{ .Release.Name }} <chart> --namespace {{ .Release.Namespace }} --reuse-values \
       --set sinks[0].kind=ClickHouseSink \
       --set sinks[0].name=default \
       --set sinks[0].spec.connection.addr=clickhouse.{{ .Release.Namespace }}.svc:9000 \
       --set sinks[0].spec.connection.credentialsSecretRef.name=clickhouse-credentials

   Past one or two fields, a values file is kinder than --set. The commented
   example in values.yaml is the tee pattern: one ClickHouse timeline and one S3
   archive, fed by two rules.
{{- end }}

A rule names exactly one sink, permanently (D14). To stream the same resources to
two backends — a queryable timeline and an immutable archive — write two rules,
one per sink: that is the tee pattern, and it is documented in docs/TEE.md.
